# Правила проекта Diony

Эти инструкции действуют для всего проекта. Все обязательные правила собраны здесь; дополнительное чтение `RULES.md` не требуется.

## Перед изменениями

- Прочитай связанные с задачей файлы, их импорты и существующие реализации похожего поведения.
- Перед созданием UI найди подходящие компоненты в `src/components/UI/` и проверь их API. Перед добавлением хука или утилиты проверь существующие реализации.
- Не принимай архитектурное решение по одному классу или скриншоту без изучения контекста.

## Структура и код

- Стек: Next.js 16, React 19, strict TypeScript, Tailwind CSS 3, TanStack Query.
- `src/app/` — маршруты и layouts. Держи route-файлы тонкими: содержимое экранов размещай в `src/screens/`.
- `src/components/UI/` — общие UI-примитивы; `src/components/` — переиспользуемые составные компоненты; `src/hooks/` — общие хуки; `src/utils/` — утилиты; `src/api/` — API-клиент.
- Используй алиас `@/*` для импортов из `src/`, два пробела, двойные кавычки, точки с запятой и завершающие запятые.
- Следуй KISS, DRY и SOLID: выбирай простое решение, не дублируй знания и логику, разделяй ответственность. Не создавай абстракции для гипотетических будущих задач.
- Существующий код не является исключением из этих правил. Соблюдай их в добавляемом и изменяемом коде; не расширяй задачу до несвязанного рефакторинга.

## UI и стили

- Используй общие UI-компоненты для кнопок, ссылок-кнопок, полей, тегов и заголовков. Не копируй их разметку и стили в экраны. Если общего компонента не хватает, расширь его API или добавь компонент в `src/components/UI/`.
- Стили компонентов пиши на Tailwind. В `src/app/globals.css` размещай только действительно глобальные стили и анимации, без стилей отдельных экранов и компонентов.
- Единственный источник палитры, типографики и брейкпоинтов — `tailwind.config.ts`. Используй существующие токены; новые значения добавляй туда, а не в локальный CSS, inline-стили или arbitrary-классы для цвета, шрифта и брейкпоинта.
- Используй полные строки Tailwind-классов или таблицы полных строк. Не собирай имена классов интерполяцией вроде `bg-${color}`: Tailwind должен находить их при сканировании исходников.
- Строй раскладку обычным потоком, flex или grid. Используй `fixed` и `sticky` только когда этого требует поведение элемента, например модального окна или закреплённой навигации. Не исправляй ошибки раскладки отрицательными отступами, `translate` или ручными смещениями; сначала исправь структуру и размеры контейнеров. Смещения для анимаций допустимы.
- Учитывай адаптивность при реализации: используй брейкпоинты из конфигурации и избегай размеров, вызывающих горизонтальное переполнение.

## Данные и загрузка

- Для клиентских запросов к серверу используй TanStack Query. Инкапсулируй запросы и мутации в переиспользуемые хуки; компоненты получают данные и запускают операции через эти хуки.
- Не добавляй `fetch`, вызовы API-клиента или запросы внутри `useEffect` непосредственно в UI-компоненты. Транспортную логику держи в `src/api/`.
- До завершения загрузки резервируй место под контент. Используй существующий `Skeleton` подходящей формы, размеры или соотношение сторон для медиа, чтобы загрузка не сдвигала раскладку. `Loader` используй для операций, где не нужно имитировать структуру контента, например внутри кнопки.

## Проверки и завершение

- После изменений кода запускай `pnpm lint` и `pnpm build` из корня проекта. После изменений только документации запуск не требуется.
- Перед завершением проверь diff на соответствие применимым правилам выше: использование общих компонентов, токенов, полных Tailwind-классов, размещение запросов и состояние загрузки.
- Не объявляй проверку успешной без её выполнения. Если команда не прошла или недоступна, укажи это и причину в результате.
- В итоговом ответе кратко укажи, что изменено и какие проверки выполнены.

## Команды и безопасность

Используй pnpm из корня проекта: `pnpm install`, `pnpm dev`, `pnpm build`, `pnpm lint`.

Не коммить environment-файлы, credentials, токены и production URL.
